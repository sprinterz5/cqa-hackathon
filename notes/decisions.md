# Решения и почему мы их приняли

Каждое решение: что выбрали, из чего выбирали, почему, на чём основано (запись в `experiments.md` или факт), что может заставить пересмотреть. Отменённые решения не удаляем, помечаем «пересмотрено» со ссылкой на новое.

## R1. Аудио: таймкоды фраз берём из общей модели Alem, а не из казахской — 2026-11-07
Выбор: `speech-to-text` с параметром `language` для всех языков, включая KZ.
Альтернатива: `speech-to-text-kk` для казахских записей.
Почему: у казахской модели на `verbose_json` пустые `segments`, текст без пунктуации, на 52 с выпала целая фраза (E25). Без таймкодов не работает перемотка записи к реплике и доказательства по звонку.
Пересмотреть, если: запись режется на куски по паузам заранее (так сделано в ветке `islam`, E23) — тогда казахская модель получает короткий кусок, а время берётся из нарезки.

## R2. Роли говорящих: определяет LLM по смыслу, одним запросом на звонок — 2026-11-07
Выбор: gpt-oss получает все фразы с номерами и возвращает роль каждой.
Альтернативы: эвристика по ключевым фразам («меня зовут», «не могу»); разделение по голосу (SpeechBrain ECAPA, ветка `islam`).
Почему: Alem не различает говорящих; эвристика по фразам на DEV даёт 47 % (E17); разделение по голосу требует ~6 ГБ локальных моделей, которых нет на ноутбуке для демо. LLM уже подключена и бесплатна.
Пересмотреть, если: разделение по голосу доступно — тогда LLM определяет роль группы голоса целиком (см. R5).

## R3. Ответ модели о ролях — с номером фразы, а не просто список — 2026-11-07
Выбор: `{"roles": [{"n": 1, "role": "operator"}, ...]}`; до 10 % пропусков заполняются ролью предыдущей фразы.
Почему: на звонках p4-ru-001 и p4-ru-004 модель дважды вернула 79 ролей на 78 фраз; строгая проверка длины отбросила ответ, сработала эвристика, полторы минуты склеились в одну реплику, итог упал 71 → 15. С номерами лишний или пропущенный элемент ничего не сдвигает.

## R4. Отсекаем галлюцинации Whisper — 2026-11-07
Выбор: выбрасываем фразы с `compression_ratio > 2,4`, с `no_speech_prob > 0,6` при `avg_logprob < −1`, и повтор предыдущей фразы слово в слово.
Почему: на p4-ru-004 под музыку ожидания распознано «Я не могу ничего сказать» × 20; это стандартные пороги самого Whisper.
Риск: настоящий повтор («Алло? Алло?») тоже будет выброшен — для оценки по чек-листу это не критично.

## R5. Гибрид аудио-цепочек (план) — 2026-11-07
Выбор: одна точка загрузки, режимы выбираются по тому, что установлено:
1. разделение по голосу из ветки `islam`, если есть его библиотеки и модели;
2. роль каждой группы голоса целиком определяет LLM (видит всё, что сказал голос);
3. без локальных моделей — облачный режим: Alem STT + роли LLM по фразам (R2, R3).
Почему: сравнение на одной метрике — см. таблицу в `experiments.md` (E26). Облачный режим нужен для демо на любом ноутбуке; локальный — для пункта «разнообразие архитектур» и приватности.

## R6. Код критерия в results.json задаётся в редакторе чек-листа — 2026-11-07
Выбор: у каждого критерия выбор из 8 кодов организаторов; индикатор «все 8 кодов назначены».
Почему: организаторы допускают новый критерий на контроле и переоценку по нему. Раньше новый критерий не получал кода, и из `results.json` пропадал, например, `empathy` — файл не по формату ровно в контрольный час.
Код не входит в ключ кэша: смена кода не вызывает переоценку.

## R7. Отдельный фильтр «Грубые ошибки» с объяснением в списке — 2026-11-07
Почему: жюри прямо сказало, что на демо попросит «показать все диалоги с грубыми ошибками и объяснить почему». Раньше они были смешаны в «требуют внимания» с низкой уверенностью и апелляциями.

## R8. Облачная цепочка остаётся режимом по умолчанию для загрузки записи — 2026-11-07
Выбор: Alem STT + роли LLM — по умолчанию; локальная цепочка `islam` — дополнительный режим, если установлены её модели.
Почему (E26): на одной метрике 62,2 % правильных реплик против 47,1 % (локальная с эвристикой) и 60,1 % (локальная с обученным классификатором); быстрее в 3–4 раза; не требует ~6 ГБ моделей, поэтому работает на любом ноутбуке и у жюри.
Пересмотреть, если: гибрид «группы голосов ECAPA + роль группы через LLM» (задача Ислама) даст заметно больше 62 % — тогда он становится режимом по умолчанию там, где модели установлены.

## R9. Одна аудио-цепочка из двух веток (слияние `islam-hybrid-roles`) — 2026-11-07
Выбор: один адрес `POST /api/dialogs/upload-audio`, одна задача в сервисе (`/api/jobs`), режим в модалке:
- облако, RU/EN/авто — весь файл в Alem `verbose_json` (наш путь);
- облако, KZ — нарезка по паузам Ислама (PyAV) + `speech-to-text-kk`;
- локально — Whisper + группы голосов ECAPA + перевод Ислама;
- роли во всех режимах — gpt-oss по фразам; в локальном режиме модель видит и метку голоса (D25).
Почему: нарезка Ислама склеивает куски с паузой < 0,75 с в фрагменты до 9 с, а смена говорящего обычно и происходит на такой паузе — фрагменты мешают двух людей сильнее, чем фразы Alem по 2–5 с; зато для казахской модели, у которой нет таймкодов, нарезка — единственный способ получить время. Разделение по голосу и перевод есть только локально — берём их там, где они установлены.
Отказались: от двух параллельных адресов загрузки и двух модалок (у каждого из нас была своя) — жюри и команда должны видеть один сценарий.

## R10. Согласие на отправку записи и запрет перезаписи — 2026-11-07
Выбор (взято из ветки `islam`): облачный режим требует галочку «Разрешаю передать запись в Alem STT»; API без неё отвечает 403. Загрузка с уже существующим ID отклоняется (раньше наш код молча перезаписывал диалог с оценками).
Почему: запись звонка — персональные данные клиента, а аудитория продукта — корпоративный заказчик. Отдельного согласия на оценку не требуем: текст и так уходит в выбранную LLM, как у чатов.
Формулировка: в локальном режиме на компьютере остаётся запись, но не текст — он идёт в LLM для ролей и оценки (README исправлен).

## R11. Нарезку фраз по говорящим оставляем включённой — 2026-11-07
Почему (E27): на одних и тех же фразах +3 правильные реплики из 209 (61,7 → 63,2 %), оба повтора совпали; ошибочная нарезка отбрасывается проверкой «слово в слово», так что вреда нет.
Важно для презентации и сравнений: облачная цепочка даёт 62–68 % в зависимости от того, как Alem нарезал запись в этот раз. Варианты сравниваем на одних и тех же фразах (`scripts/roles_variance.py`), а не по одному полному прогону.

## R12. Скрипты читают набор DEV из `data/DEV/DEV_raw.json`, если нет `data/dev_source.json` — 2026-11-07
Почему: скрипты ветки `islam` искали файл под локальным именем Ислама; у остальных набор лежит там, куда его сохраняет `scripts/fetch_dataset.py` (README). Теперь работают оба пути — проверки повторяет любой в команде.

## R13. Точность на чатах не подгоняем под 20 своих размеченных диалогов — 2026-11-07
Контекст: E34 — 132/160 (82,5 %), слабее всего c04 (13/20), c06 (15/20), казахские чаты (25/32); в заметке E34 стоит ориентир «до 99 % — 27 исправлений».
Решение: правим формулировки критериев только по правилам чек-листа и ответам организаторов, а не под отдельные метки. Каждое изменение проверяем на всех 20 диалогах и смотрим, сколько исправлений и сколько новых ошибок.
Почему: разметка наша (`reviewed_by: null`), эталон организаторов может с ней расходиться; 99 % на 20 диалогах почти наверняка означает подгонку, а на контроле будут 10 новых чатов.
