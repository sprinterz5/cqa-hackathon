# Чем мы отличаемся от других команд

## Что, скорее всего, сделает типичная команда

- Один промпт «оцени диалог по чек-листу» → JSON с баллами; итог считает сама модель.
- Чек-лист зашит в промпт или редактируется как текст; при замене критерия — переоценка всего.
- Ссылки на реплики — как модель напишет, без проверки.
- UI: список, карточка, кнопка «оспорить».
- Точность «на глаз», без замеров.

Жюри смотрит: точность против эталона (главное), функциональность, удобство, **корректность процесса** (система правда анализирует, а не выдаёт заготовки), разнообразие архитектур (локальные vs облачные LLM).

## Что стоит добавить (по соотношению эффект / усилия)

### Дёшево и сильно — делать в первую очередь

1. **Сравнение версий чек-листа** (≈1 ч). После замены критерия — таблица «было → стало» по всем диалогам: итог, изменившиеся вердикты. Прямо закрывает минуту 4 презентации и показывает, что пересчёт реальный.
2. **Прозрачность процесса** (≈30 мин). В карточке по каждому критерию: «Показать промпт и ответ модели» — точный промпт, сырой ответ, токены, время. Это прямой ответ на критерий «корректность процесса»: жюри видит, что система анализирует диалог, а не воспроизводит готовое.
3. **Экспорт в CSV/Excel** (≈30 мин). Итоги и вердикты по всем диалогам одной кнопкой — то, что QA-отдел реально будет использовать.
4. **Загрузка эталона в UI** (≈1 ч). Загрузить файл с правильными ответами → «Качество AI» считает совпадение по критериям и MAE итога. На контроле можно будет сразу показать точность, если организаторы раскроют эталон.

### Средне — если останется время

5. **Аналитика по операторам** (≈2 ч). Имена операторов уже есть в первом ответе. Дашборд: средний балл, частые провалы по критериям, языки. Для руководителя контроля качества это ценнее, чем отдельная карточка.
6. **Рекомендации оператору** (≈1–2 ч). По итогам оценки — 2–3 конкретных совета «что улучшить» со ссылками на реплики. Один дополнительный вызов модели; тон — коучинг, а не наказание.
7. **Создание критерия из описания** (≈2 ч). Пишешь «оператор предложил продукт банка» → модель предлагает конфиг критерия (тип, описание, N/A, шкала), человек правит и сохраняет. Ускоряет замену критерия на контроле.
8. **Локальный режим вживую** (≈1 ч + установка Ollama). Один диалог, оценённый Qwen3 8B на ноутбуке, рядом с облачной оценкой — сравнение точности и скорости. Закрывает пункт «разнообразие архитектур».

### Дорого или рискованно — не сейчас

9. Метрики речи по аудио (темп, паузы, перебивания) через STT Alem с временными метками слов — интересно, но в DEV только 5 звонков, а точность против эталона это не поднимет.
10. Отдельный «стандарт звонков» с Call Health Score и исходами обращений (из контекстного документа команды) — хорош как продуктовая аналитика, но в основную оценку его включать нельзя: эталон ставят по чек-листу из PDF.

## Как это рассказать (5 минут)

- **Минута 1.** Список → «Только требующие внимания» → карточка p1-ru-010.
- **Минута 2.** Баллы по критериям, клик по доказательству → реплика; N/A с причиной; «Показать промпт» (п. 2).
- **Минута 3.** Апелляция по c03 → решение проверяющего → итог 94,38 → 95,5, видны оба.
- **Минута 4.** Замена критерия в редакторе → пересчёт только его → таблица «было → стало» (п. 1).
- **Финальная фраза.** «Модель решает, что произошло, код считает баллы; мы мерили точность на своей разметке: 72% → 84%; модели открытые — Freedom может развернуть их у себя».
